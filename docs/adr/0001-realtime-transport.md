# ADR 0001: 从纯文件轮询升级为"文件 + WebSocket"混合收发接口

> ADR = Architecture Decision Record，架构决策记录——用来记录"当时面对什么问题、
> 想过哪些方案、最后选了哪个、为什么"，而不是记录代码本身长什么样(代码自己会说话，
> 但选择背后的权衡不会)。这份文档记录的是 wx_dm 从纯文件轮询(polling)升级到
> "文件 + WebSocket"混合方案的完整决策过程。

- **状态**：已采纳(Accepted)
- **日期**：2026-09-17

## 背景 / Context

wx_dm 最初的对外接口只有两个文件：`inbox.jsonl`(本脚本写，agent读)和
`outbox.jsonl`(agent写，本脚本读)。收发双向都是靠轮询(polling)：

- **收方向**：本脚本对微信iLink接口做长轮询(long polling)——发一个请求，服务器
  一直held住直到有新消息或超时才返回，比"傻轮询"(dumb polling，固定间隔无脑发请求，
  不管有没有新内容)要好，但这一段是打微信官方接口，我们改不了。
- **发方向**：本脚本自己用 `setInterval` 每秒检查一次 `outbox.jsonl` 有没有新行，
  这是纯粹的傻轮询——不管agent什么时候写的文件，最多要等接近1秒本脚本才会发现。

问题：agent那边想及时知道"微信来新消息了"，得自己想办法盯着 `inbox.jsonl`(比如
`tail -f` 或者自己写轮询逻辑去读文件)；agent想尽快把回复发出去，也得等本脚本
的1秒轮询周期。两个方向都不是"实时"的，通信成本偏高，尤其是在双方都是独立进程、
只能靠文件交换信息的前提下。

## 考虑过的方案 / Options Considered

**方案A：全部换成 `fs.watch`**
`fs.watch` 是Node.js内置的文件系统变化通知API，本质是操作系统内核级别的机制——
任何进程(不只是写文件的那个进程)都能对着一个文件/目录注册"这个文件变了请通知我"，
跨进程也能收到通知。用它替换 `outbox.jsonl` 的 `setInterval` 轮询，能让本脚本
"文件一变就立刻处理"，不用等固定周期。
但问题是：`fs.watch` 只能解决"本脚本怎么知道outbox.jsonl变了"，解决不了"agent
怎么知道inbox.jsonl变了"——因为 `fs.watch` 通知的是"文件变化"，agent那边还是得
自己对着 `inbox.jsonl` 挂一个 `fs.watch` 或者自己轮询，本质上只是把轮询这个动作
从"定时"换成"文件事件触发"，agent端的实现负担并没有减少，而且agent的技术栈可能
根本不是Node.js，不一定有对应的文件监听能力。

**方案B：全部换成 WebSocket**
WebSocket 是一个双向、常驻连接的推送通道——本脚本收到微信消息后可以直接主动推给
所有连着的客户端，agent想发回复也可以直接通过这条连接发过来，不用等任何轮询周期，
延迟最低。
但如果完全抛弃文件接口，会丢掉几个现在已经有的好处：文件是语言无关的(任何语言都能
读写一个jsonl文件，但接入WebSocket需要agent自己实现WS客户端逻辑)、文件是持久化的
(agent掉线重启后还能从文件里回溯历史，WebSocket断开连接期间推送的消息如果没有
额外的重放机制就直接丢了)、而且完全推翻现有接口意味着已经写好的agent代码全部要重写。

**方案C(最终选择)：文件接口保留，WebSocket作为额外的实时通道叠加上去**
两边都要——`inbox.jsonl`/`outbox.jsonl` 继续无条件维护(不管有没有WebSocket客户端
连着)，同时额外起一个本地WebSocket服务，把同样的事件实时推送出去，也接受agent
通过WebSocket直接发送回复。谁想用文件轮询/`fs.watch`盯文件、谁想用WebSocket拿
实时推送，agent自己选，两者互不冲突。

## 决策 / Decision

采用方案C(混合方案)，具体设计：

1. **文件接口不变**：`inbox.jsonl`/`outbox.jsonl` 照旧维护，保证语言无关、
   可持久化回溯这两个已有优点不丢。
2. **`outbox.jsonl` 的检测方式从 `setInterval` 轮询换成 `fs.watch`**：文件一变
   就立刻触发检查，同时保留一个低频(5秒)的兜底轮询，防止极少数环境下
   `fs.watch` 事件丢失(比如某些网络盘/容器场景下这个API不完全可靠)。
3. **新增本地WebSocket服务**(`ws://127.0.0.1:17894`)：
   - 微信来新消息时，除了写 `inbox.jsonl`，同时立刻广播给所有已连接客户端；
   - 客户端可以直接发 `{"reply_to":"...","text":"..."}` 让本脚本立刻发送回复，
     不用等文件轮询——发送后本脚本会把这条也补写进 `outbox.jsonl` 存档，并且
     同步跳过对应的文件行号，避免文件轮询那边重复发送同一条。
   - **只绑定 `127.0.0.1`，不绑 `0.0.0.0`**：跟文件接口一样，默认信任模型是
     "只有这台机器上的进程能访问"，绑定回环地址(loopback)能保证局域网/公网
     都连不进来，这个信任边界不能因为换了传输方式就变松。
   - **端口选 17894**，跟同项目下 `lens_extension_bridge.mjs` 已经占用的
     17893 分开，避免端口冲突。
4. **不限制同时连接的客户端数量**：允许开几个agent/操控台是部署者自己的决定，
   本脚本只保证代码层面能正确处理多个客户端同时连接、同时收广播、同时发送——
   `WebSocketServer` 自带的 `.clients` 就是一个装着所有当前连接的Set，广播时
   遍历它即可，天然支持多客户端，不需要额外写连接数上限的逻辑。
5. **顺带做了一个只读操控台**：浏览器打开 `http://127.0.0.1:17894` 能看到一个
   极简页面，通过同一个WebSocket连接实时显示收到/发出的消息，方便肉眼确认
   "这个东西到底有没有在正常工作"，不需要额外装什么客户端或者盯着终端日志刷屏。

## 为什么"两边同时发"不会导致重复发送 / Why dual-channel doesn't double-send

本脚本内部本来就维护一个 `pending` 映射表(`{ [inbox消息id]: {to_user_id, context_token} }`)，
一条消息一旦发送成功就会从这个表里删掉。不管这条回复是从 `outbox.jsonl` 文件轮询
发现的，还是从WebSocket客户端直接发过来的，走的都是同一个 `sendReply` 函数——
谁先到就删掉 `pending` 里的记录，另一边如果后到，会发现 `pending` 里已经没有
这条记录了，直接跳过并返回错误，不会真的往微信那边重复发送。这个去重机制是
现成的，不需要为了支持双通道额外设计新的去重逻辑。

## 影响与取舍 / Consequences

- agent不再"必须"通过文件轮询才能拿到消息，改善了双向延迟，但代价是多了一个
  常驻的本地服务(HTTP+WebSocket)，多了一个依赖(`ws` 这个npm包)。
- 文件接口作为"最低共同分母"继续保留，保证任何语言写的agent都至少能用最基础的
  方式接入，WebSocket是锦上添花而不是唯一选项。
- 没有做"WebSocket断线期间推送的消息重放"——如果客户端在断线期间错过了广播，
  只能靠回头读 `inbox.jsonl`/`outbox.jsonl` 补齐，这是有意保持简单(个人项目
  量级)而不是遗漏，因为文件本身已经是可靠的持久化记录了。
