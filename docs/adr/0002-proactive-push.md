# ADR 0002: 主动推送(不回复任何inbox消息) + 按sender打标签

- **状态**：已采纳(Accepted)
- **日期**：2026-09-18

## 背景 / Context

wx_dm原本的发送逻辑(`sendReply`)只支持"回复某条inbox消息"——必须有一个
`reply_to`对应`state.pending`里记录的`{to_user_id, context_token}`，而这个
`pending`记录只在"微信那边先发消息给bot"的时候才会产生。

但现在要接入的第一个真实场景(小红书爬虫定时巡逻新listing)不是"回复"，是主动
通知——爬虫发现新商品，要主动推一条消息给我，这条通知不对应任何一条我发给bot
的历史消息，`reply_to`这个概念根本不适用。同时，以后接入的agent/程序可能不止
一个(小红书爬虫、以后其他品类的监控脚本……)，如果所有通知发到微信上都长一个样，
没法一眼看出这条消息是哪个程序发的。

## 决策 / Decision

**1. 验证了主动发送不需要`context_token`。** 直接用`to_user_id`(微信用户
标识)加空的/不传`context_token`调iLink的`sendmessage`接口，实测(见对话记录，
发了一条真实测试消息到手机上)是可行的——`context_token`只是用来把回复"挂"到
某个已有会话上，不是这个接口的必要参数。这个发现让"主动推送"在协议层面完全可行，
不需要绕路。

**2. 新增`owner_user_id`概念，自动从第一条收到的消息里"偷师"。** wx_dm本来就是
单bot单主人的设计(见已知限制)，没必要让用户手动配置"我的微信id是多少"——第一个
给这个bot发消息的人，就默认是主人，`from_user_id`自动存进
`state.owner_user_id`，之后主动推送默认都发给这个人。零配置，代价是"如果有除了
主人以外的人也扫码加了这个bot并率先发了消息"会认错人，但这个场景本来就不在
设计范围内(单用户bot)。

**3. `outbox.jsonl`(以及WebSocket)新增一种消息形状**：不带`reply_to`，改带
`sender`(自己起的名字，比如`"小红书爬虫"`) + `text`。跟"回复"共用同一套
`outbox_lines_processed`去重机制和文件/WebSocket双通道设计(见
[[0001-realtime-transport]])，没有额外引入新的一致性问题。

**4. 实际发到微信上的文本自动加标签**：`【<sender>来消息】\n<text>`。这样不管
接了多少个agent进来，我在微信里一眼就能看出这条消息是谁发的，不用每次都去猜
或者去翻日志核对。

## 影响与取舍 / Consequences

- 主动推送目前只能发给唯一的`owner_user_id`，没有"发给多个人"的概念——跟整个
  项目"单用户bot"的定位一致，不是遗漏。
- 如果bot还没被任何人加过(`owner_user_id`为空)，主动推送会直接失败并报错，
  不会静默丢失或者猜一个地址乱发——错误行为要么显式失败要么显式成功，不做
  沉默的"尽力而为"。
- `sender`完全是调用方自己起的名字，wx_dm不做任何校验/白名单，这是有意的——
  wx_dm还是"纯传输层"，不应该知道"小红书爬虫"这个具体业务概念存在，`sender`
  对它来说只是一个不透明的标签字符串。
